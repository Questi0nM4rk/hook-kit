# Escalation — askpass envelope + broker protocol for hook-kit

The escalation subsystem routes `ask` decisions through a tree of session listeners up to a root harness UI. When a rule emits `.ask(...)` and `HOOK_KIT_ASKPASS` is set to a working askpass binary, the request flows through that binary (typically the bundled `hook-kit broker`) onto a per-session filesystem spool, where one or more listeners decide it. The askpass binary is the public contract; any program that reads an envelope from stdin and writes a decision to stdout is a valid responder.

This document is the source of truth for that protocol. Read it before authoring a new listener (Slack / IDE / webhook / custom UI); read it before changing the existing broker, askpass, or listener implementations under `src/escalation/`. It complements `docs/SPEC.md` § Escalation, which gives the architectural overview; this file specifies WHAT every field means, HOW the broker stages messages, and WHAT a listener must do.

The contract is `@stable @since 1.0.0` per [`docs/STABILITY.md`](./STABILITY.md). Breaking changes go through the deprecation cycle. The envelope's `PROTOCOL_VERSION` is currently `2` (shipped in 0.8). A future minor bump is the deprecation window for any envelope-shape change; the current broker rejects unknown versions with [`ProtocolVersionError`](../src/core/errors.ts).

## Envelope schema

The envelope is the JSON payload exchanged between hook → broker → listener → hook. There are two shapes: `AskRequest` (hook → listener) and `AskResponse` (listener → hook). Both are validated by Zod at every boundary.

**Source of truth.** The Zod schemas live in [`src/escalation/envelope.ts`](../src/escalation/envelope.ts) as `AskRequestSchema` and `AskResponseSchema`. The JSON-Schema form is snapshotted in [`tests/escalation/envelope-schema.snapshot.json`](../tests/escalation/envelope-schema.snapshot.json) and validated on every CI run by `tests/escalation/envelope-schema.test.ts`. The per-field semantics below mirror the schema; any drift is caught by the snapshot test.

### `AskRequest`

```ts
const AskRequestSchema = z.object({
  version: z.literal(PROTOCOL_VERSION),
  id: z.string().min(1),
  sessionId: z.string().min(1),
  parentSessionId: z.string().optional(),
  pid: z.number().int().nonnegative(),
  host: z.string().min(1),
  user: z.string().min(1),
  harness: HarnessSchema,
  toolName: z.string(),
  toolInput: z.record(z.string(), z.unknown()),
  reason: z.string(),
  label: z.string().optional(),
  annotations: z.string().optional(),
  cwd: z.string(),
  transcriptPath: z.string(),
  git: GitInfoSchema.optional(),
  createdAt: z.string(),
  expiresAt: z.string(),
});
```

| Field | Type | Required | Semantics |
|---|---|---|---|
| `version` | `2` (literal) | yes | Protocol version. Currently `PROTOCOL_VERSION = 2`. Mismatch surfaces as `ProtocolVersionError` (10th `HookKitError` subclass) — see § Protocol versioning. |
| `id` | non-empty string (UUIDv4) | yes | Request identifier. Generated by `createAskRequest` via `randomUUID()`. Used by the broker as the filename for `pending/<id>.json` and `decided/<id>.json`. |
| `sessionId` | non-empty string | yes | Hook's own session. Maps to the spool directory `~/.cache/hook-kit/sessions/<sessionId>/`. |
| `parentSessionId` | string | no | Parent in the escalation tree. When omitted, this session is a root and `forwardUp` resolves to `harness-ask`. Set automatically from `$HOOK_KIT_PARENT_SESSION_ID` or via the adapter. |
| `pid` | int ≥ 0 | yes | Originating process pid. Autofilled by `createAskRequest` to `process.pid`. Tests / specialized callers can override. |
| `host` | non-empty string | yes | Originating hostname. Autofilled from `node:os.hostname()`. |
| `user` | non-empty string | yes | Originating user. Autofilled from `$USER` / `$USERNAME` / `$LOGNAME` / `"unknown"`. |
| `harness` | `{ name: string; version?: string }` | yes | Which harness produced the ask (`{name: "claude-code", version: "1.0.0"}`, `{name: "cursor"}`, etc.). The adapter supplies this; defaults to `{ name: "unknown" }` if the adapter doesn't set it. |
| `toolName` | string | yes | Tool channel: `"Bash"`, `"Edit"`, `"Write"`, etc. Forwarded from `HookEvent.toolName`. |
| `toolInput` | `Record<string, unknown>` | yes | Tool-specific payload. For Bash: `{ command: string }`. For Write: `{ file_path: string, content: string }`. Forwarded from `HookEvent.toolInput`. |
| `reason` | string | yes | The rule's `ask` reason — what the listener sees as "why is this being asked?". |
| `label` | string | no | Decision source attribution (e.g. `"[strict-review]"`). Forwarded from the rule's decision label when set. |
| `annotations` | string | no | Pre-rendered annotation block from any warning/note decisions that fired alongside the escalate. Each line `[label] warning\|note: <msg>`. Empty/absent when no annotations fired. |
| `cwd` | string | yes | Working directory of the hook process. Forwarded from `HookEvent.cwd`. Empty string allowed (legacy adapters / tests). |
| `transcriptPath` | string | yes | Path to the harness's transcript file. Forwarded from `HookEvent.transcriptPath`. Empty string allowed. |
| `git` | `{ sha; branch?; dirty?; remote? }` | no | Optional git context. Populated only when `HOOK_KIT_ENRICH_GIT=1` is set in the binary's environment (see `src/escalation/enrich-git.ts`); failures swallow to `undefined` per Iron Law 4. |
| `createdAt` | ISO timestamp | yes | When the envelope was constructed. `new Date().toISOString()`. |
| `expiresAt` | ISO timestamp | yes | `createdAt + ttlMs` (default 60s). Metadata only — neither the broker nor `callAskpass` enforce it as a deadline by default. Listeners + observability layers may use it (audit logs, "raised X minutes ago" hints, MCP elicitation conformance). |

### `Harness` (sub-schema)

```ts
const HarnessSchema = z.object({
  name: z.string().min(1),
  version: z.string().optional(),
});
```

The adapter populates `name` from the harness it bridges (`"claude-code"`, `"cursor"`, `"raw"`). `version` is opportunistic — set when the adapter can detect the harness version, omitted otherwise.

### `GitInfo` (sub-schema)

```ts
const GitInfoSchema = z.object({
  sha: z.string().min(1),
  branch: z.string().optional(),
  dirty: z.boolean().optional(),
  remote: z.string().optional(),
});
```

Populated by `enrichGit(cwd)` when `HOOK_KIT_ENRICH_GIT=1`. Each field comes from one `git -C cwd …` invocation; failures are swallowed to `undefined` per Iron Law 4. Listeners that want git context for their UI read from this field.

### `AskResponse`

```ts
const AskResponseSchema = z.object({
  id: z.string().min(1),
  decision: z.enum(["allow", "deny", "harness-ask"]),
  reason: z.string().optional(),
  by: z.string().optional(),
  decidedAt: z.string(),
});
```

| Field | Type | Required | Semantics |
|---|---|---|---|
| `id` | non-empty string | yes | Echoes the `AskRequest.id` this response answers. The askpass driver fails the request when `request.id !== response.id` — protects against response confusion. |
| `decision` | `"allow" \| "deny" \| "harness-ask"` | yes | Listener's verdict. `allow` lets the command run silently. `deny` blocks with the `reason`. `harness-ask` delegates upstream to the harness's native UI (root-chain fall-through, see § Tree semantics). |
| `reason` | string | no | Free-form explanation surfaced to the user / agent. |
| `by` | string | no | Audit attribution: which listener decided (`"tui:pid12345"`, `"broker:validator"`, `"broker:auto-deny"`, `"mockAskpass"`). |
| `decidedAt` | ISO timestamp | yes | When the listener wrote the decision. |

The response has no `version` field — version validation runs on the request only. A listener that responds with a malformed envelope is denied by the askpass driver via `EnvelopeValidationError`.

### Protocol versioning

The envelope's `version` field is a Zod `z.literal(PROTOCOL_VERSION)` so any mismatch fails parsing. `parseAskRequest` pre-validates the field and throws [`ProtocolVersionError`](../src/core/errors.ts) directly, surfacing version skew separately from generic shape errors. Concretely:

- **Same version** (`request.version === 2`): accepted, parsing continues to Zod shape validation.
- **Legacy version** (`request.version === 1`): rejected with `ProtocolVersionError(source: "parseAskRequest", expected: 2, actual: 1)`. The broker propagates this class verbatim (does NOT re-wrap as `EnvelopeValidationError`) and synthesizes a deny reason `[hook-kit broker] protocol version mismatch: ...`. Observability layers route version skew separately from shape errors.
- **Future version** (`request.version === 99`, `3`, etc.): same as legacy — rejected with `ProtocolVersionError`. A future minor bump is the deprecation window for any envelope-shape change.
- **Missing `version` field**: falls through to Zod's shape validation, surfaces as `EnvelopeValidationError` (generic). `ProtocolVersionError` fires only when the field exists but does not match.

Listeners and parallel-version-support callers can `instanceof ProtocolVersionError` to handle version skew explicitly (e.g. log "deploy your listener fleet first" instead of "envelope is malformed"). See `tests/escalation/broker-version.test.ts` for the contract tests.

## Broker protocol

The bundled `hook-kit broker` is the default askpass implementation. Unlike many IPC contracts that use Unix sockets or line-delimited JSON streams, the broker stages messages on a **filesystem spool** with atomic `O_EXCL` writes. This is deliberate (see [`docs/SPEC.md`](./SPEC.md) § Why this shape — "Filesystem spool inside the broker"): inspectable, crash-safe, atomic via `rename(2)` semantics, no daemon strictly required.

### On-disk layout

```text
~/.cache/hook-kit/sessions/<sessionId>/
├── meta.json                   # {sessionId, parentSessionId?, startedAt, pid}
├── pending/<requestId>.json    # AskRequest envelopes (one per ask in flight)
├── decided/<requestId>.json    # AskResponse envelopes (one per resolved ask)
├── listeners/<pid>.lock        # ListenerMarker liveness records — one per attached listener
└── audit.jsonl                 # append-only log of all events for this session
```

The root defaults to `join(homedir(), ".cache", "hook-kit", "sessions")` (see `DEFAULT_ROOT` in [`src/escalation/broker.ts`](../src/escalation/broker.ts)). Override via `BrokerAskpassOptions.root` for tests and specialized deployments. Directory permissions are `0o700` (owner-only); file permissions are `0o600`. No tokens, no auth — same-user processes only.

### Message framing

There is **no socket** and **no line-delimited JSON stream**. Messages are exchanged via the filesystem:

- **Request:** the hook process writes the `AskRequest` as JSON to `pending/<id>.json` using `writeFileSync(path, data, { flag: "wx", mode: 0o600 })`. The `wx` flag is `O_EXCL` semantics: succeeds only if the file does not exist. First-writer-wins; a duplicate request id is rejected with a deny.
- **Response:** a listener writes the `AskResponse` as JSON to `decided/<id>.json` using the same atomic `O_EXCL` flag. First-writer-wins gives a free input queue when multiple listeners try to answer simultaneously.

The broker (running as the hook's askpass binary) polls `decided/<id>.json` until either the file appears or the caller process is killed. The poll interval defaults to 100ms (see `DEFAULT_POLL_MS` in `src/escalation/broker.ts`).

### Wire format on stdin/stdout

The askpass driver (`callAskpass` in [`src/escalation/askpass.ts`](../src/escalation/askpass.ts)) and the broker (`brokerAskpass` in [`src/escalation/broker.ts`](../src/escalation/broker.ts)) communicate stdin-in / stdout-out:

1. `callAskpass` spawns `$HOOK_KIT_ASKPASS` with `stdin: "pipe"`, writes `JSON.stringify(request)`, closes stdin.
2. The askpass binary reads stdin, decides, writes `JSON.stringify(response)` to stdout, exits.
3. `callAskpass` reads stdout, parses through `parseAskResponse`, validates `response.id === request.id`, returns the response.

Errors:

- Askpass spawn failure → `ProcessSpawnError` + synthesized deny.
- Askpass exit non-zero → deny with stderr-tail in reason.
- Empty stdout → deny "askpass produced no output".
- Unparseable stdout → `EnvelopeValidationError` + synthesized deny.
- Response id mismatch → deny "askpass response id mismatch".
- Optional `timeoutMs` exceeded → `proc.kill("SIGKILL")` + synthesized deny.

The full failure-mode contract lives in `callAskpass`'s JSDoc and [`docs/SPEC.md`](./SPEC.md) § Askpass Contract.

### Public broker functions

```ts
// Resolve the on-disk paths for a session. Does not touch the filesystem.
export function brokerPaths(sessionId: string, root?: string): BrokerPaths;

// Ensure the spool tree exists. Idempotent.
export function ensureSession(
  sessionId: string,
  opts?: { parentSessionId?: string; root?: string },
): BrokerPaths;

// Drive the broker in askpass mode: parse request, validate listener
// presence, stage on pending/, poll decided/, return response.
export function brokerAskpass(
  stdinText: string,
  opts?: BrokerAskpassOptions,
): Promise<AskResponse>;

// Snapshot all session spools currently on disk.
export function listSessions(opts?: ListSessionsOptions): SessionInfo[];

// Snapshot pending requests for one session.
export function listPending(sessionId: string, opts?: { root?: string }): AskRequest[];

// Atomically submit a decision. Returns true if accepted (first-writer wins).
export function submitDecision(
  sessionId: string,
  requestId: string,
  decision: AskDecisionKind,
  reason?: string,
  opts?: SubmitDecisionOptions,
): boolean;
```

`brokerPaths`, `ensureSession`, `listSessions`, `listPending`, `submitDecision`, and `brokerAskpass` are the bundled-broker primitives a listener needs. They are `@internal` for v1.0 — listeners that want listener-style polling should follow the `examples/escalation-listener-stdout/` pattern, which uses these primitives but does not re-export them. The askpass binary itself remains the public escalation contract; broker primitives may be promoted to `@stable` in a future minor based on listener demand.

## Lifecycle

A single ask request walks through 5 phases. Each phase corresponds to specific code in `src/escalation/`:

```text
1. ensureSession
   ┌──────────────────────────────────────────────────────────────────┐
   │ mkdir -p ~/.cache/hook-kit/sessions/<sid>/{pending,decided}      │
   │ write meta.json (sessionId, parentSessionId?, startedAt, pid)    │
   │ -- broker.ts: ensureSession                                      │
   └──────────────────────────────────────────────────────────────────┘
                            │
2. registerListener         │  (concurrent with phase 1; can happen
   ┌────────────────────────▼──────────────────────────────────────────┐
   │ mkdir -p <session>/listeners                                      │
   │ writeFileSync listeners/<pid>.lock = ListenerMarker JSON          │
   │ return cleanup() to remove on graceful exit                       │
   │ -- listeners.ts: registerListener                                 │
   └───────────────────────────────────────────────────────────────────┘
                            │
3. atomic pending write     │  (hook process, via callAskpass → brokerAskpass)
   ┌────────────────────────▼──────────────────────────────────────────┐
   │ parseAskRequest(stdin)  -- ProtocolVersionError or                │
   │                            EnvelopeValidationError on failure     │
   │ hasParentListener(sid)  -- NO PARENT ATTACHED deny when zero      │
   │ writeFileSync pending/<id>.json with O_EXCL                       │
   │ append audit.jsonl                                                │
   │ -- broker.ts: brokerAskpass                                       │
   └───────────────────────────────────────────────────────────────────┘
                            │
4. poll decided/            │  (broker loops; listener writes)
   ┌────────────────────────▼──────────────────────────────────────────┐
   │ for (;;) {                                                        │
   │   if existsSync(decided/<id>.json) → parseAskResponse → exit loop │
   │   if timeoutMs exceeded → synthesize auto-deny, exit              │
   │   sleep(pollMs)                                                   │
   │ }                                                                 │
   │ -- broker.ts: brokerAskpass poll loop                             │
   │ -- listener writes decided/<id>.json via submitDecision           │
   │    (atomic O_EXCL, first-writer-wins)                             │
   └───────────────────────────────────────────────────────────────────┘
                            │
5. cleanup                  │
   ┌────────────────────────▼──────────────────────────────────────────┐
   │ rmSync pending/<id>.json + decided/<id>.json                      │
   │ append audit.jsonl with kind="decided" + decision + by            │
   │ return AskResponse to callAskpass → callAskpass returns to engine │
   │ engine maps response.decision → terminal: deny | null | ask       │
   │ -- broker.ts: brokerAskpass cleanup tail                          │
   └───────────────────────────────────────────────────────────────────┘
```

The lifecycle is the same whether the responder is the bundled broker, a custom Slack-bridge askpass, or the `examples/escalation-listener-stdout/` worked example. The differences live in phase 4 (who writes `decided/<id>.json`) and how the listener wires into phase 2 (when does it register, when does it cleanup).

### Failure modes per phase

| Phase | Failure | Typed error | Outcome |
|---|---|---|---|
| 1 | `mkdir -p` fails (permissions, disk full) | `FileWriteError` on stderr | Throws; the hook's `handleError` adapter catches and exits non-zero. |
| 2 | listener marker write fails | `FileWriteError` on stderr | `registerListener` throws; cleanup never registers. |
| 3 | envelope unparseable JSON | `EnvelopeValidationError` | Fail-CLOSED: stderr + synthesized deny `id: "<malformed>"`. |
| 3 | envelope `version` mismatch | `ProtocolVersionError` | Fail-CLOSED: stderr + synthesized deny with version details. |
| 3 | no live listener in parent chain | (no error class, validator result) | Synthesized deny `"NO PARENT ATTACHED"`, by=`"broker:validator"`. |
| 3 | duplicate request id (UUID collision) | (no error class) | Synthesized deny `"duplicate request id"`. |
| 4 | decision file malformed | `EnvelopeValidationError` | Fail-CLOSED: stderr + synthesized deny + audit `decision-malformed`. |
| 4 | `timeoutMs` elapses | (no error class) | Synthesized auto-deny, by=`"broker:auto-deny"`, audit `auto-deny`. |
| 5 | cleanup `rmSync` fails | `FileWriteError` on stderr | Best-effort: emit + continue. Response still returned. |

## Listener authoring

A listener is any process that watches a session spool and writes decisions to `decided/<id>.json`. Listeners are NOT broker-mediated — they participate in the same spool the broker writes to. The bundled `hook-kit watch` TUI is a listener; the `examples/escalation-listener-stdout/` worked example is a listener; a Slack-bridge daemon would be a listener.

Every listener does three things:

### 1. Detect pending requests

The listener registers a marker (so the broker's NO PARENT ATTACHED validator sees it as live), then polls `pending/` for new request files. Two primitives:

```ts
// Mark this process as a live listener for the session. Returns a cleanup
// function that removes the marker on graceful exit. Stale markers (process
// gone) are pruned on the next scan via kill(pid, 0) liveness probe.
import { registerListener } from "@questi0nm4rk/hook-kit/escalation";
const detach = registerListener(sessionId, "watch");
// ... register SIGINT/SIGTERM handlers to call detach() ...

// Snapshot current pending requests for a session.
import { listPending } from "@questi0nm4rk/hook-kit/escalation";
const pending = listPending(sessionId); // AskRequest[]
```

The listener should poll `listPending` on a sensible interval (`hook-kit watch`'s TUI uses 250ms via `DEFAULT_POLL_MS`; a less-interactive listener can poll less frequently). Each `AskRequest` carries everything needed to decide: `reason`, `toolName`, `toolInput`, `cwd`, optional `git`, optional `annotations` block.

### 2. Decide or forward

Three terminal outcomes:

```ts
// Decide locally — write decided/<id>.json with O_EXCL.
import { submitDecision } from "@questi0nm4rk/hook-kit/escalation";
const ok = submitDecision(sessionId, requestId, "allow", optionalReason, {
  by: `my-listener:pid${process.pid}`,
});
// ok=false means another listener already decided (first-writer-wins).
```

```ts
// Punt up the parent chain — one synchronous hop. If no parent in meta.json,
// writes harness-ask into decided/<id>.json; the hook's adapter renders that
// as the harness's native UI (CC's permissionDecision: "ask").
import { forwardUp } from "@questi0nm4rk/hook-kit/escalation";
const result = await forwardUp(sessionId, requestId);
// result.kind = "forwarded" | "harness-ask" | "missing-pending"
```

```ts
// Take no action — let another listener or the broker's timeout handle it.
// First-writer-wins ensures multiple listeners can compete safely.
```

The choice depends on the listener's role:

- A user-facing TUI (`watch-tui.ts`) decides locally on `a`/`d` keystrokes; forwards on `e`.
- A parent-agent observer watching `--children-of $MY_SESSION_ID` decides on policy match, forwards otherwise.
- An audit-only listener never decides; it tails `audit.jsonl` and posts to a log sink.

### 3. Respond

The actual write is `submitDecision` (which calls `createAskResponse` + atomic `O_EXCL` write to `decided/<id>.json`) or `forwardUp` (which writes to the parent's `pending/`, then copies the parent's decision down). After the write:

- The broker process polling `decided/<id>.json` reads the response, cleans up `pending/` + `decided/`, returns to `callAskpass`.
- `callAskpass` parses, validates id-match, returns the response to the engine.
- The engine renders the response through the adapter (allow → silent, deny → deny terminal, harness-ask → adapter delegates to the harness UI).

### Reference listener implementations

- [`src/escalation/watch-tui.ts`](../src/escalation/watch-tui.ts) — interactive terminal listener with `↑↓` navigation, `a`/`d`/`e`/`q` keystrokes, detail pane. Use this when the listener IS a human at a TTY.
- [`src/escalation/forward.ts`](../src/escalation/forward.ts) — the synchronous escalate-up forwarder. NOT a standalone listener (it's a hop primitive other listeners call); shown here as the canonical "one-hop, copy decision back down" implementation.
- [`examples/escalation-listener-stdout/`](../examples/escalation-listener-stdout/) — the worked example. ~60-line stdout-prompt listener that downstream consumers fork for Slack / IDE / webhook integrations.

## Tree semantics

Each running hook-kit invocation is a node in a tree. The root is the harness's native human-UI prompt (CC's `permissionDecision: "ask"`); below the root, agent + subagent sessions form the tree.

```text
[ root: harness UI (CC native ask) ]
            │
[ agent session ]
        ├── [ subagent session A ]
        │       └── [ sub-subagent session ]
        └── [ subagent session B ]
```

Each session's `meta.json` carries a `parentSessionId` pointer. When the broker's NO PARENT ATTACHED validator walks the chain, it follows these pointers (cycle-safe via a visited set).

### `parentSessionId` walk

```ts
// listeners.ts: hasParentListener
export function hasParentListener(sessionId: string, opts?): boolean {
  const visited = new Set<string>();
  let current: string | undefined = sessionId;
  while (current !== undefined && !visited.has(current)) {
    visited.add(current);
    if (liveListeners(current, opts).length > 0) {
      return true;
    }
    current = readParentId(current, opts);
  }
  return false;
}
```

The validator at phase 3 of the lifecycle uses this walk: at least one live listener (any session in the chain) must exist before the broker accepts the request. Zero live listeners anywhere → synthesized deny `"NO PARENT ATTACHED"`. This surfaces misconfigured plugins immediately instead of hanging on the hook timeout.

### `forwardUp` semantics

```ts
// forward.ts: forwardUp
//  1. Read pending/<id>.json from the source session.
//  2. Look up meta.json.parentSessionId from the source.
//  3a. No parent → write harness-ask into source's decided/<id>.json. End.
//  3b. Parent exists → ensureSession(parentSessionId) + atomic O_EXCL write
//      of envelope (with forwarded_from: sessionId added) into parent's
//      pending/<id>.json. Then poll parent's decided/<id>.json. When parent's
//      decision lands, copy it down to source's decided/<id>.json.
```

Multi-hop chains compose by recursion: each level's listener can independently `forwardUp`. The forwarder is synchronous (no daemon, no event watcher), bounded by the original hook process's lifetime — when the harness's hook timeout kills the hook, every blocked forwarder up the chain unblocks too.

There is no per-hop timeout by default. A test or specialized caller can pass `timeoutMs` to `forwardUp` for bounded waits.

### Root behavior — `harness-ask`

When `forwardUp` exhausts the chain (no parent in `meta.json`), the source session's `decided/<id>.json` gets a `harness-ask` response. The hook's adapter sees the `harness-ask` decision and renders it as the harness's native UI:

- **CC adapter (`src/adapters/claude-code.ts`):** emits `permissionDecision: "ask"` in the JSON output, surfacing CC's native ask prompt.
- **Shell wrapper (`src/wrapper/hk.ts`):** emits stdout `[hook-kit] needs review: <reason>` + exit 1.
- **Custom adapter:** documented in `docs/ADAPTERS.md` § Output convention.

The harness UI is itself a responder — `harness-ask` is not silent-allow. Iron Law 4's exception (fail-closed when ask is broken) does not apply at the root; the harness UI tier is the canonical responder of last resort.

### `HOOK_KIT_ASKPASS` env-var contract

The env var is the single switch that routes ask decisions through the escalation infrastructure. Three states:

| State | Behavior |
|---|---|
| **Unset** | No broker infrastructure configured. `callAskpass` returns a synthesized `harness-ask` response immediately. The adapter delegates to the harness UI. Use this for simple "ask the user" hooks that don't need a broker tree. |
| **Set, working** | `callAskpass` spawns the binary, writes the envelope, reads the response. The full broker/listener tree is in play. |
| **Set, broken** (binary missing, non-executable, exits non-zero, malformed stdout) | `callAskpass` emits a typed error to stderr and synthesizes a deny with reason `[hook-kit] askpass …`. This is the Iron Law 4 exception — when infra was *expected* but broken, fail-CLOSED. |

The bundled `hook-kit broker` is the default askpass implementation but not the only one. Any program that reads a JSON envelope from stdin and writes a decision JSON to stdout is a valid askpass: `/bin/true` (always-allow), `/bin/false` (always-deny), a Slack-bridge, a GitHub-issue-bridge. The contract is the envelope schema + the wire format, not the broker spool.
