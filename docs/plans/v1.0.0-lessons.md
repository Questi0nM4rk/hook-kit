# v1.0.0 implementation — lessons learned

**Purpose:** every phase's subagent reads this BEFORE starting. Each completed phase appends what was learned: what worked, what broke, patterns to repeat or avoid, surprises about the codebase. The goal is monotonic improvement — phase N+1 doesn't repeat phase N's mistakes.

**Discipline:** lessons are written by the reviewing human (not the subagent), AFTER tests run. Tag each entry with the phase that produced it. Keep entries short — rule + WHY + how-to-apply, one block each. If a lesson is repo-wide, also promote to `CLAUDE.md`.

---

## How to use this doc (subagent instructions)

When invoked for phase M`N`:

1. **Read this entire file before touching any task.** Lessons may invalidate task descriptions in `v1.0.0-tasks.md` — if a lesson contradicts a task's verify step, follow the lesson and note the conflict in your final report.
2. **Read `docs/plans/v1.0.0.md` and `docs/plans/v1.0.0-tasks.md`** to scope the phase.
3. **Implement only the tasks in your assigned phase.** Do not pre-implement future-phase tasks even if you see the opportunity. If you find a blocker that requires future-phase work, stop and report — don't silently expand scope.
4. **Verify every task with the verify step from the tasks doc.** If a verify step is impossible or wrong, that's a finding — report it, propose a fix, but do not silently substitute a weaker verification.
5. **Mark each task `[x]` in the tasks doc only after its verify step passes.** Honest accounting; partial tasks stay `[~]`.
6. **No drive-by refactors.** If you see something to clean up that isn't in your phase's scope, note it for a follow-up. Don't expand the phase.
7. **Test discipline:** every new public API ships with a test in the same PR. Tests live where the existing convention says they live (`tests/` for regular, `tests-isolated/` for anything using `mock.module()`).
8. **External validation only.** Don't claim "looks right." Run the test / lint / typecheck and cite the exit code.

## Phase M0 — Foundation

Completed 2026-05-21. 10/10 tasks done. One subagent (batch model), one /simplify pass, full test/lint/typecheck green.

### Lessons

**L1. tsconfig `include` must cover every dir you typecheck.**

- Subagent reported `bun run typecheck` exit 0, but the editor's diagnostics flagged 20+ type errors in `scripts/check-stable-exports.ts` and `scripts/check-changelog.ts`. Root cause: `tsconfig.json` `"include": ["src", "tests"]` — `scripts/` was silently skipped. Fixed by adding `"scripts"` and `"tests-isolated"` to include.
- **Why:** "typecheck passes" is meaningless if tsc doesn't see the files. The black-box review caught this because editor diagnostics use a broader include heuristic than CI tsc.
- **How to apply:** Any phase that adds a new top-level directory (`bench/`, `examples/adapter-template/`, etc.) MUST either extend the root tsconfig `include` glob OR ship its own `tsconfig.json`. Subagent prompts for M1+ should call this out explicitly. Verify with `bun tsc --noEmit --listFiles | grep <new-dir>/` to confirm tsc actually parsed the new dir.

**L2. Per-symbol `@stable @since 1.0.0` tags are CI-load-bearing — do NOT collapse.**

- `/simplify` flagged "per-symbol @stable redundant in pure-stable files; collapse to file-header" as MEDIUM. Skipped because TASK-002's verify step `grep -B2 "^export" src --include="*.ts" | grep -c "@stable"` depends on per-symbol counts. Collapsing would silently defeat the grep verify and break the CI guard.
- **Why:** TSDoc tooling reads file-header tags but a regex grep doesn't cascade them down to each `export`. Two consumers of the same JSDoc tag have different cascade rules; per-symbol satisfies both.
- **How to apply:** When tagging stability, default to per-symbol. Only use file-header tags in files where EVERY export shares the tier AND no grep-based check counts them. Future tag passes (e.g., `@since 1.1.0` for new APIs) should also be per-symbol.

**L3. Extract shared CI-script lib at script #2, not later.**

- M0 shipped two CI scripts (`check-stable-exports.ts`, `check-changelog.ts`) with identical `git()` + `commitRangeMessages()` + similar argv parsing. `/simplify` flagged the duplication; extracted to `scripts/_lib.ts` post-hoc. Cost: a refactor commit after the original 9 commits.
- **Why:** Two copies is the drift-floor. At copy #3 the divergence has already cost edit cycles per copy.
- **How to apply:** When a phase ships >1 file in a new directory (scripts/, bench/, examples/*/), the subagent prompt should explicitly require: "if two files share a helper of any kind, extract to a sibling `_lib.ts` (or similar) in the first PR." Don't ship the duplication and refactor later.

**L4. JSDoc tag content should be SHORT — one-line WHY, not paragraphs.**

- M0 subagent added many `@internal` blocks. `/simplify` flagged 5-10-line blocks where 1-2 would do. One file (`watch-tui.ts`) ended up with two consecutive headers in different comment styles. Fixed.
- **Why:** Verbose JSDoc rots faster than the code it documents and is harder to scan during reviews.
- **How to apply:** Subagent prompts for M1+ that involve tagging should say: "Tags are `@<tag>` + ≤1 sentence WHY. No multi-paragraph blocks. If you find yourself writing a paragraph, the explanation belongs in the file body or a sibling doc, not the JSDoc."

**L5. Subagent's "open questions" are LOAD-BEARING signal — resolve before next phase.**

- M0 subagent surfaced 5 ambiguities it resolved one way but flagged for confirmation:
  - CI-vs-lefthook for changelog enforcement (chose CI)
  - `src/engine/index.ts` @internal vs per-symbol (chose per-symbol)
  - `HookKitErrorCode` transitive export
  - JSDoc placement at declaration site vs barrel
  - tests/ + tests-isolated/ tagging
- Each is a small bet. Resolved silently they compound into surface drift before 1.0 lock.
- **How to apply:** Subagent prompts for M1+ should either: (a) pre-empt obvious ambiguities in the brief, OR (b) require the subagent to STOP mid-execution and ask via the team chat for any decision with shipped-surface impact. Don't let the subagent pick five paths it isn't sure about.

### Workflow notes (process, not code)

- **Black-box review caught the typecheck gap.** The editor's diagnostic stream surfaced what `bun run typecheck` missed. M1+ reviewer should always run `bun run typecheck` AND look at the editor diagnostic count for the changed files; mismatch = include-glob gap or similar config skip.
- **/simplify findings were 80% real, 20% wrong-context.** F5 (collapse @stable) was a false positive in this context (broke CI grep). Trust /simplify but verify against the spec before applying. Skipping a finding with a written reason is fine.
- **The batch model (one subagent for all 10 tasks) worked for M0** because the tasks were small and largely independent. For M1+ where tasks have real implementation behind them (DecisionObserver API, SqliteStateStore, etc.), micro-slice per the user's directive: 1-3 tasks per subagent invocation, each with its own tests + verify pass, then aggregate.
- **Subagent verify rigor:** the subagent ran every TASK-NNN verify command and quoted exit codes in the report. That's the bar. M1+ subagents must do the same; reviewer can spot-check, but the subagent owns proving each task done.

### Surprises about the codebase

- `src/escalation/` is bigger than expected (7 files, ~1000 lines of broker/listener/forwarder/TUI). The M1.4 escalation contract spec task will be larger than the roadmap estimated.
- `bun-types` package covers `process`, `Bun`, `node:fs`, `node:path` cleanly — no need for separate `@types/node` install. Future scripts should rely on `bun-types`.
- The existing test split (`tests/` + `tests-isolated/` with separate `bun test` invocations) is enforced by `package.json` `test` script. Don't regress.

### Batch S1a — lefthook scaffolding (completed 2026-05-21)

Two commits: `lefthook@1.13.6` devDep + `lefthook.yml` with biome-fix + commit-msg conventional. Lower-ceremony review (config-only batch; skipped /simplify per L-S1a-2 rationale below).

**L-S1a-1. Verify fixtures must respect the project's actual lint config.**

- Brief's verify fixture `var foo = 'bar';` could NOT auto-fix because biome's `noUnusedVariables` rule (already at error in our biome.jsonc) blocks `--write` from persisting any fix when other errors remain. Subagent had to switch to `export var foo = 'bar';` to satisfy the unused-var rule first. The `var → const` rewrite ALSO didn't happen because biome 2.x's `useConst` declines to rewrite `export var` (export semantics ambiguity).
- **Why:** biome's `--write` is all-or-nothing per file. Any unresolvable lint error blocks all fixes from persisting. Test fixtures that touch ANY lint rule with no auto-fix will silently fail the demo even though the formatter-fixable parts work.
- **How to apply:** For verify fixtures in future batches (S2 strict biome, S3a/b ESLint), use lint-free fixtures that ONLY touch formatter rules (whitespace, quote style, semicolons, line width). NEVER mix lint rules with the auto-fix demo. Or: do the demo on an explicitly-disabled rule.

**L-S1a-2. Lower-ceremony review IS appropriate for config-only batches.**

- S1a shipped `lefthook.yml` (16 lines), `package.json` (+2 lines), `bun.lock` updates. No TypeScript code added. Running /simplify on YAML + JSON would have been theater. Verified by reading both files directly + spot-checking hook shim install.
- **Why:** /simplify's three-agent review (reuse/quality/efficiency) is calibrated for code-with-control-flow. Pure config has no reuse / no flow / no perf surface.
- **How to apply:** S1b (gitleaks/codespell/markdownlint configs), S5 (CI yaml) — all config-only. Skip /simplify; spot-read instead. S2 (strict biome forces real code edits to fix violations), S3a/b (ESLint setup + rule violations), S4 (suppress-comment script in TS) — those DO need /simplify because real code lands.

**L-S1a-3. Subagent prompts referencing CLI flags need version-checked.**

- Brief told subagent to use `bun lefthook run commit-msg --commit-msg-file <path>`. That flag does not exist in lefthook 1.13.6 (and may never have). Correct invocation: positional `bun lefthook run commit-msg <path>`. Subagent caught it and adapted, but the brief should not have said the wrong thing.
- **Why:** I copy-pasted from a generic lefthook example without verifying against the installed version. Subagent's time partially wasted on brief reconciliation.
- **How to apply:** When briefing a subagent with CLI command-line examples, either (a) verify the exact invocation against the installed CLI version first, or (b) tell the subagent "verify the flag exists in the installed version before using; adapt if needed and report."

**L-S1a-4. `bun.lock` is gitignored — devDep version pinning relies on package.json alone.**

- Subagent noted: `.gitignore` excludes `bun.lock`, so the new `lefthook@1.13.6` pin is held only by `package.json`'s exact version (no caret). For reproducible installs across contributors / CI, this is fragile — `bun install` will resolve to the package.json constraint but transitive devDeps drift silently.
- **Why:** Bun's default has been to gitignore the lockfile; the npm/pnpm/yarn ecosystem committed to lockfile-in-repo. hook-kit inherited Bun's default.
- **How to apply:** **Surface to user as a S1b prereq decision.** Either: (a) un-gitignore `bun.lock`, commit it, get reproducible builds; or (b) accept transitive drift and pin via `package.json` exact versions only. ai-guardrails un-gitignores per the discipline-import principle. Hook-kit should probably follow but it's a policy call, not a M0.5 implementation detail.

**L-S1a-5. `lefthook install` writes `.git/hooks/prepare-commit-msg` too** (lefthook's own cleanup shim). Expected, harmless, informational only — every developer's `.git/hooks/` will have it.

### Batch S1b — gitleaks + codespell + markdownlint (completed 2026-05-22)

Three commits: gitleaks hook (no devDep — system binary), codespell hook + `.codespellrc`, markdownlint hook + `markdownlint-cli2@0.22.1` devDep + `.markdownlint.jsonc`. Lockfile updated atomically in the T05 commit (the first M0.5 batch since `bun.lock` was un-gitignored). Lower-ceremony review (config-only).

**L-S1b-1. Tool-specific allowlists invalidate generic security fixtures.**

- Brief told subagent to verify gitleaks with `aws_access_key_id = "AKIAIOSFODNN7EXAMPLE"`. That's in gitleaks 8.x's built-in allowlist (canonical AWS docs example key — gitleaks deliberately ignores it). Subagent had to switch to a real-shape OpenSSH private-key fragment in a `.txt` file to trigger the hook.
- **Why:** Security tools curate allowlists to avoid false positives on documentation examples. A "secret-looking" fixture might not actually look like a secret to the tool.
- **How to apply:** When briefing security-tool verify steps, use real-shape (but test-only) credentials, not famous example values. Prefer non-AWS shapes when possible (gitleaks has more AWS allowlist entries than others). The OpenSSH-key-in-.txt-file pattern works; document if you find a cleaner one.

**L-S1b-2. Spell-check ignore-words mix two distinct categories — document both.**

- Subagent seeded `ignore-words-list` with `unparseable` (valid English variant) and `absout` (deliberate variable name `absOut` in build/bundle.ts). Both belong, for different reasons. Header comment in `.codespellrc` calls out the rationale per entry.
- **Why:** Without rationale, future contributors can't tell "this is a legitimate English word codespell flags wrongly" from "this is a project-specific identifier we deliberately chose." Same risk as un-justified `// eslint-disable`.
- **How to apply:** Every new ignore-words entry needs a one-line WHY in the config header. If the entry is project-identifier-specific (like `absout`), document the file:line context. Future S4 (suppression-comment discipline) will codify this for code suppressions too.

**L-S1b-3. markdownlint defaults conflict with conventional doc formats — disable selectively.**

- Four rules tripped on existing repo docs:
  - **MD024** (no duplicate headings) — Keep-a-Changelog requires `### Added` / `### Fixed` per version. Fix: `{ "siblings_only": true }` — allows the cross-version reuse, still forbids same-level adjacency.
  - **MD060** (table-column-style) — stylistic. Pick a side; we kept padded for readability and disabled.
  - **MD040** (fenced code language tag) — common gotcha on prose-y blocks (shell-output examples, ASCII trees). Fix: tag with `text` or `shell`. Subagent fixed 8 instances in README/CHANGELOG/CLAUDE.md.
  - **MD041** (first line H1) — disabled per S1a brief; some docs lead with a context paragraph.
- **Why:** markdownlint's defaults are optimized for blog-style markdown; library README / changelog formats deviate.
- **How to apply:** When introducing markdownlint downstream (or in S1b-equivalent batches in other repos), audit against the project's actual docs first. The four-rule disable pattern above is a sane starting point for Keep-a-Changelog + table-heavy README.

**L-S1b-4. Subagent auto-merged the branch via lefthook-during-commit chain.**

- Subagent's 3 commits landed directly on main without a manual `wt merge` step. Likely path: subagent committed in its worktree → `wt` configured to auto-rebase-and-fast-forward on commit when the working tree is clean and tests pass (or the subagent ran `wt merge` itself before returning). Either way, the M0.5 review loop's "subagent reports done → reviewer runs `wt merge`" step was short-circuited.
- **Why:** Net positive (one less manual step) but means the reviewer can't black-box the worktree branch before merge — work is already on main when the report arrives.
- **How to apply:** For batches where the review must precede merge (S2 strict biome — real code changes; S3a/b ESLint adoption — same), the subagent prompt should explicitly say "do NOT run wt merge; leave the branch on its worktree for reviewer." For config-only batches (S1b confirmed; S5 likely) auto-merge is fine.

**L-S1b-5. Editor diagnostics can be stale right after worktree removal.**

- After cleaning up the 2 leftover worktree dirs (M0 + S1a husks), the editor flooded with "Cannot find module" diagnostics across half of `src/`. Was tsc-server reindexing; `bun run typecheck` returned exit 0 immediately.
- **How to apply:** Diagnostic floods after major worktree/branch operations are likely stale; verify with `bun run typecheck` before panicking.

### Batch S2 — strict biome adoption (completed 2026-05-22)

8 commits: enable-all-groups + 11 disable-at-config + Qwik disable + lefthook biome-pin + codespell `afterall` allow + noMagicNumbers re-enable per override + auto-fix combined --safe+--unsafe + CHANGELOG + comment nit-fix. 66 files changed +735/-274. 891 initial violations resolved across the pipeline. 525/525 tests still pass, CP-1 clean.

**L-S2-1. STOP-on-threshold discipline pays off.**

- Subagent stopped twice during S2: once at the initial 12-rules-over-threshold gate (surfaced for Q1-Q5 reviewer decisions), once at the `useBlockStatements` Q1+Q3 mutual-unsatisfiability discovery. Each STOP produced a correct reviewer decision instead of a silent compromise that would have shipped a bad config.
- **Why:** the subagent's per-rule violation manifest + impact assessment is the right level of detail for the reviewer to make tier-defining calls. Subagent doing it silently would have either over-disabled or over-churned.
- **How to apply:** keep the ≥20-in-src/ STOP rule in S3a/b briefs. Add a second STOP trigger: "if your work surfaces a brief contradiction (like Q3 vs Q1 for useBlockStatements), STOP and surface it — don't pick a path silently to resolve the contradiction."

**L-S2-2. Initial "no --unsafe" gate was over-cautious; Q3 reversal in flight worked cleanly.**

- The reviewer's original Q3 (no --unsafe) was about preventing noProcessGlobal/noNodejsModules import rewrites. Once those got disabled-at-config, the underlying concern vanished. Subagent surfaced the contradiction; reviewer authorized --unsafe; commit landed clean.
- **Why:** general-purpose "no --unsafe" was the right precaution INITIALLY (before knowing what would be enabled), but became a liability once specific cross-cutting rules were disabled.
- **How to apply:** for future "what's the auto-fix budget" decisions, condition the answer on which rules are enabled. Don't bake general rules that assume a rule set that may change during execution. Pattern: "no --unsafe IF rules X/Y/Z are enabled" rather than "no --unsafe ever."

**L-S2-3. Biome's `correctness` group includes framework-specific rules (Qwik, etc.) that fire on plain TS.**

- After T06 enabled `correctness: "error"`, `useQwikValidLexicalScope` fired 8 times in src/build/cli.ts / src/builders/command.ts / src/engine/index.ts on plain function expressions. Hook-kit is not a Qwik project; rule is irrelevant. Disable-with-reason landed as commit `c14d3c1` per the standard pattern.
- **Why:** biome's groups bundle framework-aware rules with general correctness rules. Group-shorthand `"error"` enables ALL members, including framework-specific.
- **How to apply:** when group-enabling biome rules in S3a (or future versions), expect 1-3 framework-specific rules to fire. Discover them in the first lint run post-enable; disable-at-config with reason. Document the running list in `biome.jsonc` so future biome upgrades that add more framework rules slot in cleanly.

**L-S2-4. Pre-commit biome must use the project pin (`bunx --bun biome`), not bare `biome`.**

- System `biome` at `/usr/bin/biome` (Arch package, 2.3.15) was being invoked by the lefthook pre-commit. Project pin is `@biomejs/biome@2.4.15` in devDependencies. Schema-version mismatch + unknown-rule errors (useQwikValidLexicalScope wasn't in 2.3.15) blocked the T07b commit until `bedba16` fixed the hook invocation.
- **Why:** lefthook YAML's `run: biome check` follows PATH lookup. PATH ordering varies per environment; nothing forces it to prefer the local devDep.
- **How to apply:** every lefthook command that calls a project devDep must use `bunx --bun <tool>` (or the equivalent invocation pattern that pins to the local node_modules) instead of bare `<tool>`. Applies retroactively to S1b's gitleaks/codespell/markdownlint hooks if those tools ever get added as project devDeps (currently they're system binaries; if they move, the same fix applies).

**L-S2-5. Auto-fix volume scales with rule severity changes; combined --safe+--unsafe commit is the right shape.**

- Going from `recommended: true` (~10 rules at error) to all-groups-at-error (~150 rules at error) produced 235 auto-fixable violations across 28 files. The single combined commit (`03738df`) bundled --safe (noNegationElse, useNumericSeparators, etc.) + --unsafe (useBlockStatements, noUselessUndefined, etc.) into one reviewable diff with a content-bearing commit body.
- **Why:** alternative was 7-10 tiny per-rule commits, each adding overhead with no review benefit. The mechanical nature of auto-fixes makes them reviewable as one batch.
- **How to apply:** for S3a/b (ESLint adoption), expect similar volume from the typescript-eslint preset. One combined "apply --fix auto-fixes" commit per linter is the right shape.

**L-S2-6. biome 2.x file-header disable syntax: `// biome-ignore-all lint/<group>/<rule>: <reason>`.**

- Distinct from per-line `// biome-ignore <rule>: <reason>` — the file-header form requires the `lint/` prefix AND the rule name with group prefix (`lint/style/noMagicNumbers`). Subagent shipped 14 file-header disables in the right form.
- **How to apply:** when writing S3a/b briefs that mention file-header disables, cite this exact syntax. Don't invent variants.

### Batch S3a — ESLint scaffolding (completed 2026-05-22)

3 commits: eslint 10.4.0 + typescript-eslint 8.59.4 devDeps, `eslint.config.js` flat with `strictTypeChecked` + `stylisticTypeChecked` presets, lint script split into `lint:biome` + `lint:eslint`. 182 ESLint violations surfaced (medium band) for S3b to resolve.

**L-S3a-1. Subagent cwd persistence between Bash calls is treacherous in worktrees.**

- Subagent's first 3 commits accidentally landed on `main` because `cd ~/Projects/hook-kit && ...` patterns shifted persistent cwd OUT of the worktree. Recovered via `git reset --hard 55facae` on main (dropped accidental commits) + `git reset --hard 1857b0c` on worktree branch (pulled the commits in). End state correct, but the recovery was load-bearing.
- **Why:** Bash tool's cwd persists across calls. Subagent's brief said "use `cd` only into the worktree", but a single `cd ~/Projects/hook-kit && git log` for inspection silently moved subsequent commits to main.
- **How to apply:** Future subagent briefs MUST say: "Either `cd` into your worktree path ONCE at session start and use relative paths thereafter, OR always pass `-C <worktree-path>` to git and `--cwd <worktree-path>` to bun. NEVER `cd` to a different directory mid-session — Bash cwd persists." Bake into the S3b/S4 briefs explicitly.

**L-S3a-2. `parserOptions.projectService: true` is the modern typescript-eslint 8+ pattern.**

- Replaces `project: true`. Auto-discovers nearest tsconfig per file; faster; handles multi-tsconfig setups. Used here with `tsconfigRootDir: import.meta.dirname` for absolute resolution.
- **How to apply:** any future typescript-eslint config additions should use `projectService` not `project`.

**L-S3a-3. Intentional redundancy on `no-unused-vars`** — keep BOTH biome's `noUnusedVariables` AND `@typescript-eslint/no-unused-vars`. Type-aware variant catches strict superset (destructured fields, type-only imports). Biome's non-type-aware version catches drift if ESLint mis-parses. First flagger fails CI. Documented in `eslint.config.js` comment.

**L-S3a-4. `strict-type-checked` + `stylistic-type-checked` produced 182 violations across 36 files.** Three rule families dominate (78%): `no-unsafe-*` (67), template/void expression discipline (45), async-correctness (32). Medium-band per S3b sizing — tractable in one batch with rule-family triage.

**L-S3a-5. typescript-eslint presets are 100% error-severity out of the box** (verified by grep against the package's flat config files). Zero `warn` defaults. CP-1 holds without per-rule overrides.

### Batch S3b — strict ESLint rule resolution (completed 2026-05-22)

8 commits: T12 async-correctness overrides + T13 auto-fix (26 sites) + 5 per-family manual passes (no-floating-promises 22, require-await 10, no-unsafe-* 67, restrict-template-expressions 32, final-pass 24) + T14 CHANGELOG. 37 files changed, +337/-124. 182 ESLint violations → 0. 525/525 tests still pass, CP-1 clean across all 3 configs.

**L-S3b-1. Subagent found 4 latent test bugs while fixing `require-await`.**
- `expect(promise).rejects.toThrow(...)` without `await` silently passes in bun-test (the matcher's TS type is `void` even though runtime is async). Tests claiming to verify rejection behavior were succeeding regardless of whether the rejection matched. Subagent rewrote 4 to `try { await p } catch(e) { ... }`.
- **Why:** type system can't catch async-unawaited assertions when the matcher's declared type is sync. The lint rule that surfaced it (`@typescript-eslint/require-await`) catches the missing await indirectly via "async without await."

### CP-1. NO `warn` SEVERITY IN ANY STATIC-CHECK CONFIG — Binary: `error` (blocks) or `off` (explicitly disabled with reason)

**The rule.** Every lint / static-analysis tool we configure (biome, ESLint when it lands in S3a, any future scanner) MUST use `"error"` or `"off"` severity. `"warn"` / `"warning"` / `"info"` are **forbidden** in our configs. If something matters enough to flag, it matters enough to block. If it doesn't matter enough to block, disable it explicitly with a one-line WHY.

**Why.**

- Warning fatigue: warnings accumulate and get ignored. "X warnings" in CI output becomes background noise; the genuinely important new warning hides among the chronic ones.
- Forced decision: "make it pass or disable it" forces an explicit, reviewed decision per rule. There is no "I'll address it later" middle ground that silently becomes "never."
- Honest CI signal: `bun run lint` exit 0 means "every enabled rule passes." It cannot mean "passes except for the 47 chronic warnings we've stopped reading."
- Consistent with project ideology: hook-kit's own decision vocabulary uses `deny` (block) and `ask` (decide explicitly) terminals; `warning` / `note` are annotations that ALWAYS run alongside an explicit decision. The lint stack mirrors: every flagged rule produces a decision (error/off), never a "kinda flag."

**Scope.**

- ✅ Applies to: biome.jsonc rule severities, ESLint rule severities (S3a+), any future codespell-like config that has severity levels.
- ❌ Does NOT apply to: hook-kit's `warning` decision kind (that's an annotation produced by RULES at runtime for end-user agent feedback, totally separate concept). lefthook `fail_text` (already binary — hook either passes or blocks). markdownlint defaults (binary). codespell (binary). gitleaks (binary).

**Concrete applications.**

- S2 (strict biome): every rule in the 7 groups must end up `"error"` or `"off"`. Use `"off"` with a one-line WHY for rules we deliberately disable (the WHY goes in a sibling comment, JSONC-style). Never `"warn"`.
- S3a/b (ESLint): same — every rule from `strict-type-checked` + `stylistic-type-checked` + any extras lands as `error` or `off-with-reason`. If `@typescript-eslint`'s recommended preset defaults a rule to `warn`, explicitly upgrade or disable.
- Future: same applies to any new tooling. When porting from ai-guardrails or elsewhere, audit severity levels before merging the config; flip any `warn` to a deliberate `error` / `off` decision in the porting commit.

**Verify command for future audits.**

```bash
grep -inE '"(warn|warning|info)"' biome.jsonc .eslintrc.* eslint.config.* lefthook.yml 2>/dev/null
# Expect: zero matches. Any match is a rule violation.
```

**This rule was set 2026-05-22 in response to the M0.5 phase. It is durable — applies to every future batch, every future tool, every future repo policy port. Promote to the consumer-facing project README's "How we keep code quality" section if/when one is written.**
