# v1.0.0 implementation — lessons learned

**Purpose:** every phase's subagent reads this BEFORE starting. Each completed phase appends what was learned: what worked, what broke, patterns to repeat or avoid, surprises about the codebase. The goal is monotonic improvement — phase N+1 doesn't repeat phase N's mistakes.

**Discipline:** lessons are written by the reviewing human (not the subagent), AFTER tests run. Tag each entry with the phase that produced it. Keep entries short — rule + WHY + how-to-apply, one block each. If a lesson is repo-wide, also promote to `CLAUDE.md`.

---

## How to use this doc (subagent instructions)

When invoked for phase M`N`:

1. **Read this entire file before touching any task.** Lessons may invalidate task descriptions in `v1.0.0-tasks.md` — if a lesson contradicts a task's verify step, follow the lesson and note the conflict in your final report.
2. **Read `docs/plans/v1.0.0.md` and `docs/plans/v1.0.0-tasks.md`** to scope the phase.
3. **Implement only the tasks in your assigned phase.** Do not pre-implement future-phase tasks even if you see the opportunity. If you find a blocker that requires future-phase work, stop and report — don't silently expand scope.
4. **Verify every task with the verify step from the tasks doc.** If a verify step is impossible or wrong, that's a finding — report it, propose a fix, but do not silently substitute a weaker verification.
5. **Mark each task `[x]` in the tasks doc only after its verify step passes.** Honest accounting; partial tasks stay `[~]`.
6. **No drive-by refactors.** If you see something to clean up that isn't in your phase's scope, note it for a follow-up. Don't expand the phase.
7. **Test discipline:** every new public API ships with a test in the same PR. Tests live where the existing convention says they live (`tests/` for regular, `tests-isolated/` for anything using `mock.module()`).
8. **External validation only.** Don't claim "looks right." Run the test / lint / typecheck and cite the exit code.

## Phase M0 — Foundation

Completed 2026-05-21. 10/10 tasks done. One subagent (batch model), one /simplify pass, full test/lint/typecheck green.

### Lessons

**L1. tsconfig `include` must cover every dir you typecheck.**
- Subagent reported `bun run typecheck` exit 0, but the editor's diagnostics flagged 20+ type errors in `scripts/check-stable-exports.ts` and `scripts/check-changelog.ts`. Root cause: `tsconfig.json` `"include": ["src", "tests"]` — `scripts/` was silently skipped. Fixed by adding `"scripts"` and `"tests-isolated"` to include.
- **Why:** "typecheck passes" is meaningless if tsc doesn't see the files. The black-box review caught this because editor diagnostics use a broader include heuristic than CI tsc.
- **How to apply:** Any phase that adds a new top-level directory (`bench/`, `examples/adapter-template/`, etc.) MUST either extend the root tsconfig `include` glob OR ship its own `tsconfig.json`. Subagent prompts for M1+ should call this out explicitly. Verify with `bun tsc --noEmit --listFiles | grep <new-dir>/` to confirm tsc actually parsed the new dir.

**L2. Per-symbol `@stable @since 1.0.0` tags are CI-load-bearing — do NOT collapse.**
- `/simplify` flagged "per-symbol @stable redundant in pure-stable files; collapse to file-header" as MEDIUM. Skipped because TASK-002's verify step `grep -B2 "^export" src --include="*.ts" | grep -c "@stable"` depends on per-symbol counts. Collapsing would silently defeat the grep verify and break the CI guard.
- **Why:** TSDoc tooling reads file-header tags but a regex grep doesn't cascade them down to each `export`. Two consumers of the same JSDoc tag have different cascade rules; per-symbol satisfies both.
- **How to apply:** When tagging stability, default to per-symbol. Only use file-header tags in files where EVERY export shares the tier AND no grep-based check counts them. Future tag passes (e.g., `@since 1.1.0` for new APIs) should also be per-symbol.

**L3. Extract shared CI-script lib at script #2, not later.**
- M0 shipped two CI scripts (`check-stable-exports.ts`, `check-changelog.ts`) with identical `git()` + `commitRangeMessages()` + similar argv parsing. `/simplify` flagged the duplication; extracted to `scripts/_lib.ts` post-hoc. Cost: a refactor commit after the original 9 commits.
- **Why:** Two copies is the drift-floor. At copy #3 the divergence has already cost edit cycles per copy.
- **How to apply:** When a phase ships >1 file in a new directory (scripts/, bench/, examples/*/), the subagent prompt should explicitly require: "if two files share a helper of any kind, extract to a sibling `_lib.ts` (or similar) in the first PR." Don't ship the duplication and refactor later.

**L4. JSDoc tag content should be SHORT — one-line WHY, not paragraphs.**
- M0 subagent added many `@internal` blocks. `/simplify` flagged 5-10-line blocks where 1-2 would do. One file (`watch-tui.ts`) ended up with two consecutive headers in different comment styles. Fixed.
- **Why:** Verbose JSDoc rots faster than the code it documents and is harder to scan during reviews.
- **How to apply:** Subagent prompts for M1+ that involve tagging should say: "Tags are `@<tag>` + ≤1 sentence WHY. No multi-paragraph blocks. If you find yourself writing a paragraph, the explanation belongs in the file body or a sibling doc, not the JSDoc."

**L5. Subagent's "open questions" are LOAD-BEARING signal — resolve before next phase.**
- M0 subagent surfaced 5 ambiguities it resolved one way but flagged for confirmation:
  - CI-vs-lefthook for changelog enforcement (chose CI)
  - `src/engine/index.ts` @internal vs per-symbol (chose per-symbol)
  - `HookKitErrorCode` transitive export
  - JSDoc placement at declaration site vs barrel
  - tests/ + tests-isolated/ tagging
- Each is a small bet. Resolved silently they compound into surface drift before 1.0 lock.
- **How to apply:** Subagent prompts for M1+ should either: (a) pre-empt obvious ambiguities in the brief, OR (b) require the subagent to STOP mid-execution and ask via the team chat for any decision with shipped-surface impact. Don't let the subagent pick five paths it isn't sure about.

### Workflow notes (process, not code)

- **Black-box review caught the typecheck gap.** The editor's diagnostic stream surfaced what `bun run typecheck` missed. M1+ reviewer should always run `bun run typecheck` AND look at the editor diagnostic count for the changed files; mismatch = include-glob gap or similar config skip.
- **/simplify findings were 80% real, 20% wrong-context.** F5 (collapse @stable) was a false positive in this context (broke CI grep). Trust /simplify but verify against the spec before applying. Skipping a finding with a written reason is fine.
- **The batch model (one subagent for all 10 tasks) worked for M0** because the tasks were small and largely independent. For M1+ where tasks have real implementation behind them (DecisionObserver API, SqliteStateStore, etc.), micro-slice per the user's directive: 1-3 tasks per subagent invocation, each with its own tests + verify pass, then aggregate.
- **Subagent verify rigor:** the subagent ran every TASK-NNN verify command and quoted exit codes in the report. That's the bar. M1+ subagents must do the same; reviewer can spot-check, but the subagent owns proving each task done.

### Surprises about the codebase

- `src/escalation/` is bigger than expected (7 files, ~1000 lines of broker/listener/forwarder/TUI). The M1.4 escalation contract spec task will be larger than the roadmap estimated.
- `bun-types` package covers `process`, `Bun`, `node:fs`, `node:path` cleanly — no need for separate `@types/node` install. Future scripts should rely on `bun-types`.
- The existing test split (`tests/` + `tests-isolated/` with separate `bun test` invocations) is enforced by `package.json` `test` script. Don't regress.
