# v1.0.0 plan — kit-layer stabilization for downstream policy products

**Status:** draft.
**Author:** session 2026-05-20.
**Scope philosophy:** hook-kit is the *kit* between `@questi0nm4rk/shell-ast` (parse / AST / wrapper-unwrap) and downstream policy products (ai-guardrails, third-party guardrail bundles). 1.0 promises a stable, semver-promised extension surface that downstream consumers can compose enterprise-grade products on top of — without forking the kit or hitting kit-layer gaps every other sprint. 1.0 does NOT ship policy, audit sinks, identity bindings, or curated rule bundles; those live in downstream consumers.

This release closes the 0.x line. After 1.0, breaking changes follow semver: one minor-version deprecation cycle, then removal at the next major.

---

## What 1.0 promises

1. **Semver islands.** Three stability tiers:
   - **STABLE** (semver-promised, breaking change = major bump): everything re-exported from `src/index.ts`, everything under the `./testing` subpath, the `ProtocolAdapter` interface, the `StateStore` interface, the askpass envelope schema (`src/escalation/envelope.ts` schema only — not the implementation), the broker socket protocol.
   - **EXPERIMENTAL** (subject to minor-version breakage with one-release deprecation): `coverageReport` and any new testing-SDK analytics, the SQLite store binding-level details (the interface is STABLE, the schema is EXPERIMENTAL until 1.2).
   - **INTERNAL** (no stability promise, may move/rename in any release): `src/engine/internals.ts`, `src/escalation/broker.ts` implementation details, `src/escalation/listeners.ts`, `src/escalation/watch-tui.ts`, anything under `src/build/`.
2. **Deprecation cycle.** Any STABLE removal: one minor-version warning (compile-time deprecation comment + runtime console.warn once-per-session) before removal at the next major.
3. **Extension points are real.** Downstream products can build adapters, state stores, askpass listeners, and decision observers without modifying the kit.

## What 1.0 explicitly does NOT ship

- **Curated rule bundles.** Lives in downstream consumers. `examples/ai-guardrails/` is the reference, not the deliverable.
- **Audit sinks (syslog / OTLP / Splunk HEC / Datadog).** Consumers wire these via the `DecisionObserver` API shipped in M1.
- **Identity / role / SSO binding.** Consumers extend `EvalContext` with whatever identity model their product needs.
- **Threat model for any specific policy.** Consumers own the threat model for what their bundle prevents; the kit ships a "what the kit can and cannot see" doc only (M2.4).
- **Central policy distribution / signed bundle delivery.** Consumers own bundle distribution; the kit ships the `bun build --compile` path and that's it.
- **MCP / Cursor / Cline / Copilot adapters.** Adapter template + contract documentation only. Specific adapters ship in downstream products or as opt-in 1.x additions on demand.
- **ML-based intent detection.** Out of scope architecturally. Stay structural.
- **Management UI.** CLI + library + signed bundle binary is the whole product.
- **Rule serialization to JSON/YAML for hot-loading.** Rules are TypeScript compiled to a binary. Same model as eBPF programs and OPA Rego bytecode. Document the choice; do not build hot-reload.

### M1 — Extension points (the kit's whole point)

#### 1.1 `DecisionObserver` API

**Goal:** programmatic, schema-stable access to every decision the engine emits, so downstream consumers can sink to syslog / OTLP / HEC / file / custom transport without parsing wrapper stdout.

**Current state:** decisions surface only via the adapter's output side (CC adapter emits JSON to stdout per CC protocol; shell wrapper emits formatted text). No programmatic hook.

**Design sketch:**

```ts
// src/core/types.ts
export interface DecisionEventRecord {
  readonly timestamp: number;
  readonly ruleId: string;          // module.id + ":" + rule.kind + ":" + N
  readonly ruleKind: string;        // "command" | "path" | "pipe" | "redirect" | "content" | "custom" | "stateful"
  readonly decision: "deny" | "ask" | "warning" | "note" | "error";
  readonly reason: string;          // decision.reason or annotation.message
  readonly label?: string;          // decision.label if set
  readonly event: {
    readonly eventName: string;
    readonly toolName: string;
    readonly cwd: string;
    readonly sessionId: string;
    // toolInput.command hashed (sha256) — full input NOT logged by default
    readonly toolInputHash: string;
  };
  readonly timingMs: number;        // wall-clock time spent in rule.evaluate
}

export interface DecisionObserver {
  /** Called synchronously per terminal decision and per annotation.
   *  Observers MUST NOT throw — exceptions are caught and surfaced as
   *  an `error` annotation on the outcome, but the decision proceeds.
   *  For async sinks, the observer should enqueue and flush
   *  out-of-band. */
  onDecision(record: DecisionEventRecord): void;
}

// src/engine/index.ts — EvaluateOptions
export interface EvaluateOptions {
  // ...existing fields...
  readonly observers?: readonly DecisionObserver[];
}
```

**Acceptance:**

- [ ] Type lives in `src/core/types.ts`, re-exported from `src/index.ts`.
- [ ] Engine fires observers per terminal decision AND per annotation.
- [ ] Observer throw is caught and surfaced as `error` annotation; engine proceeds.
- [ ] Timing measured per-rule via `performance.now()`.
- [ ] `toolInputHash` is sha256 of `JSON.stringify(toolInput)`; full input NOT included in the record by default (prevents secrets leaking to logs by default).
- [ ] Tests in `tests/engine/observer.test.ts`: fires per decision, fires per annotation, throw-safety, timing recorded, hash is deterministic across runs.
- [ ] `docs/SPEC.md` § Observability gets a new section documenting the contract and the hash policy.

**Dependencies:** M0 (stability marking).
**Risks:** Synchronous observers blocking the engine if a consumer writes a slow sink. Mitigation: doc says "enqueue and flush out-of-band"; ship a `BufferedObserver` reference in M4 testing SDK.
**Estimate:** M.

#### 1.5 `StateStore` concurrency contract spec

**Goal:** make `stateful()` rules safe to deploy on shared infra (CI runners, multi-worker daemons, long-lived broker processes).

**Current state:** `StateStore` interface is 5 methods (`get / set / has / delete / flush`). Two implementations: `MemoryStateStore` (single-process, in-memory), `TmpdirStateStore` (single-process, JSON file). Neither is concurrent-safe. No spec on atomicity or cross-process semantics.

**Design sketch:** spec lives in `src/core/types.ts` JSDoc on the `StateStore` interface AND in new `docs/STATE.md`.

Required guarantees:

- **Atomicity:** every `set` / `delete` is atomic with respect to concurrent readers. A reader sees either the pre-state or the post-state, never a torn intermediate.
- **Flush semantics:** `flush()` durability — after `flush()` resolves, all prior writes are visible to fresh stores opened against the same backing storage, AND are recoverable across process restart.
- **Concurrent stores:** multiple `StateStore` instances pointing at the same backing storage MUST safely interleave. Last-write-wins per key. Reads see the latest committed write.
- **No transactions, no multi-key atomicity in 1.0.** A single key's read-modify-write is the consumer's problem; document the pattern (read → mutate → set; on conflict, retry).

**Acceptance:**

- [ ] JSDoc on `StateStore` interface enumerates the four guarantees.
- [ ] `docs/STATE.md` covers: contract, the read-modify-write pattern, examples of safe vs unsafe consumer code, what each shipped store provides.
- [ ] `MemoryStateStore` documented as "single-process only — process-wide locks satisfy the contract trivially."
- [ ] `TmpdirStateStore` either upgraded to honor the contract (file locking via `flock` or `open(O_EXCL)`) OR documented as "violates the concurrent-store guarantee; use SqliteStateStore for multi-process work" with a doc comment + runtime warning when more than one instance opens the same file.

**Dependencies:** M0.
**Risks:** if TmpdirStateStore upgrade is non-trivial on Windows (different file-lock semantics), defer Windows support to 1.1.
**Estimate:** M.

#### 3.2 `subshell()` builder

**Goal:** match commands inside `$(…)` and backtick subshells, distinct from `bash -c` recursion which goes through the inline-shell recursion path.

**Current state:** the engine doesn't currently inspect subshells. shell-ast can find them; hook-kit doesn't dispatch into them.

**Design sketch:** detect `CmdSubst` nodes via shell-ast walk; recurse into their stmts list as a synthetic evaluation similar to inline-shell. Builder:

```ts
export function subshell(rule: Rule): Rule;
// Wraps any rule so it fires when the rule would fire ON A SUBSHELL'S contents.
// Example: subshell(cmd("rm").withFlag("-rf"))  fires on  `echo $(rm -rf /tmp)`
```

**Acceptance:**

- [ ] Subshell detection via walk.
- [ ] Recursion through `CmdSubst.stmts` synthesizing inner events.
- [ ] Tests: positive (subshell hides banned cmd, rule fires), negative (no subshell, rule doesn't fire), nested subshells, subshell inside `bash -c`.
- [ ] Document the depth-cap interaction (counts against MAX_RECURSE_DEPTH).

**Risks:** subshell semantics differ between bash/posix/mksh edge cases. Acceptance: cover bash semantics correctly; document posix/mksh as best-effort if any divergence shows up.
**Estimate:** M.

#### 4.2 Cross-rule conflict detection

**Design sketch:**


## Open questions

These need resolution during M0–M1; flagging now so they don't surprise later.

1. **Sync vs async observers in 1.1.** Sync is simpler and matches the per-rule timing model. But a downstream consumer wanting to ship to an HTTP endpoint synchronously would block evaluation. Current proposal: sync invocation, doc says "enqueue and flush out-of-band, do not perform I/O in the observer." Alternative: async invocation with a documented latency budget. Decide before 1.1 implementation.
2. **Is `src/escalation/` a STABLE public API surface, or only the envelope schema + broker socket protocol?** Current proposal: only the schema + protocol are STABLE; the implementation (broker.ts, listeners.ts, watch-tui.ts) is INTERNAL. Confirm during 1.4 documentation.
3. **`bun:sqlite` vs `better-sqlite3` for SqliteStateStore.** `bun:sqlite` is faster but Bun-only. `better-sqlite3` works on Node but requires native compilation. Decide during 2.1; document the choice and the consumer-runtime implications.
4. **Should `frequency()` ship without SqliteStateStore?** Memory / tmpdir stores work but degrade under concurrency. Proposal: ship `frequency()` in M3.4 but document that production use requires SqliteStateStore (M2.1). Order matters; don't release frequency() before sqlite.
5. **WASM preloading.** shell-ast already exports `preloadWasm` (verified in current source). hook-kit's `run()` / `runShell()` could call it eagerly to amortize cold-start. Discussion item: do we always preload, opt-in via flag, or leave to consumer? Default-preload is friendliest for compiled binaries; opt-in is friendlier for library mode where the consumer parses asynchronously anyway.
6. **`unparse` exposure.** shell-ast may add roundtrip in its own 1.0; if it does, hook-kit could support rule-driven command rewrites (rule says "deny + suggested-replacement: <unparsed AST>"). Out of scope for hook-kit 1.0; revisit in 1.x if shell-ast ships it.

## Risks

1. **Scope creep into ai-guardrails territory.** Pressure to ship "just a few rules" or "just a syslog sink" — resist. The kit's value is in NOT being the product. Every scope-creep decision logs as `DECISION:` in the session that makes it.
2. **shell-ast major-version bumps mid-development.** shell-ast also pursuing 1.0; if its API shifts, hook-kit may rev. Mitigation: coordinate timeline; aim for hook-kit 1.0 release ~2 weeks after shell-ast 1.0 to absorb any last shape changes.
3. **Performance regression from observer API overhead.** Calling observers on every decision adds work even when no observers are registered. Mitigation: short-circuit `if (observers.length === 0)` at evaluate entry; bench in M2.2.
4. **SqliteStateStore platform issues.** WAL files on Windows behave differently; bun:sqlite has no Windows release yet (as of writing). Mitigation: explicitly scope 1.0 SqliteStateStore to Linux + macOS; Windows in 1.1 or via better-sqlite3 fallback.
5. **Adapter contract changes after publishing as STABLE.** Once `docs/ADAPTERS.md` ships the contract is locked. Mitigation: extend test coverage on the two reference adapters before locking; add a third tiny adapter (test-only) that exercises edge cases.
6. **Bun version churn.** Bun is pre-2.0; APIs we depend on (`Bun.spawn`, `bun:sqlite`, `bun build --compile`) can shift. Mitigation: pin a known-good Bun version in CI; document the supported Bun range.

## Lessons applied from 0.x

Carried forward into 1.0 implementation discipline:

- **Zero silent fails.** Every internal failure path constructs a typed `HookKitError`. New code in this release inherits the pattern; observer-throw is the new boundary added in M1 — fail-open with `error` annotation.
- **Test isolation discipline.** Any test using `mock.module()` lives under `tests-isolated/`. CI runs `bun run test` (the two-invocation script), not raw `bun test`.
- **Annotated tags only.** Per `qsm-worktrunk` rules, all release tags are `git tag -a`. Lightweight tags don't push via `--follow-tags`.
- **Conventional commits.** Every release commit uses `feat:` / `fix:` / `refactor:` / `docs:` / `test:` / `chore:` per `git-workflow.md`.
- **CHANGELOG every commit.** `[Unreleased]` section updated in the same commit as the change; cut to `1.0.0` heading at release time.
