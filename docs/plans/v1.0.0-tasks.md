# v1.0.0 task list — granular work items

**Source:** decomposes [`v1.0.0.md`](./v1.0.0.md) into atomic work items.
**Audience:** anyone picking up a single PR-sized chunk of 1.0 work.
**Status:** draft, ready to seed an issue tracker.

---

## Conventions

| Field | Meaning |
|---|---|
| **ID** | `TASK-NNN` — stable identifier; never renumber. Skipped numbers are reserved for inserts. |
| **Outcome** | The concrete artifact that exists after this task is done. |
| **Verify** | A command, file path, or test name that proves the task is complete. If a human has to subjectively eyeball it, the task is not granular enough — split it. |
| **Size** | XS (≤2h), S (≤1d), M (2–4d), L (≥1w). If L, consider splitting. |
| **Depends** | Other TASK IDs that must be complete first. |

**Workflow:**
1. Claim a task by assigning yourself in the tracker (or filing a `gh issue` against this doc).
2. Open a feature branch (`wt add feat+task-NNN-short-slug`).
3. Conventional commit messages reference the task: `feat(observer): add DecisionEventRecord type [TASK-012]`.
4. Mark done by checking the box `[x]` AND landing the PR. Both required.
5. If verification fails, the task is not done — fix or split.

---

## Status legend

- `[ ]` — open, unclaimed
- `[~]` — in progress (claim by adding your handle: `[~] @me`)
- `[x]` — done, verified, merged

## Notes on task discipline

- **Don't batch task completions.** Check the box and merge each as a self-contained PR. Long-running branches with 10+ tasks merged at once defeat the verification model.
- **If a task's `Verify` step doesn't pass, the task isn't done.** Resist the urge to mark `[x]` "in spirit." If verification needs to change because the task scope shifted, edit the verification step in the same commit that changes the scope.
- **If a task feels too big (>L), split it.** Open new tasks (TASK-159, TASK-160, …) and add `Depends: TASK-XYZ-split` to the original. Never silently grow a task.
- **Tasks under M0 block tasks in M1–M5.** Don't start M1 work until M0 is fully green; the stability tags are load-bearing for the rest of the plan.
- **M2.1 (SqliteStateStore) is on the critical path for M3.4 (frequency).** Sequence accordingly when claiming work.
- **Roadmap drift discipline.** If implementing a task reveals the roadmap (`v1.0.0.md`) was wrong, update the roadmap in the same PR as the task fix. Don't let the roadmap diverge silently from the actual code.
